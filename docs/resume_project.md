## ⚠️ 诚信声明：本文件的使用规则

### 1. 本文件里的每一个数字，只属于三类之一

| 标注 | 含义 | 证据边界 |
|---|---|---|
| **【已实现】** | 仓库里存在对应源码/脚本/产物，任何人可独立打开文件核对 | 可复现；但"文件在库"不等于"我本次执行过" |
| **【设计目标】** / **【设计计算】** | 由参数推导出来的目标值、阈值或设计算式，**没有任何实测支撑** | 只能推导，不能声称"测出来是" |
| **【仿真】** | 来自 `firmware/BSP/host/` 物理模型或 `simulator/` 的结果 | 只能说明"在模型里是这样"，不能说明"在真机上是这样" |

正文中每一处涉及数字的表述，都用方括号标出它属于哪一类。**没有标注的数字，就是本文件的错误。**

另有一条必须说清楚的边界：本文件的"【已实现】"指**文件在库、可被独立执行验证**。本次撰写**未运行任何 Python 脚本、未编译任何 C 代码**（仓库中也不存在 CMake/Makefile，见 §声明5）。因此凡是转述 `host/selftest.py` 各项检查的判定条件，都是**按脚本内的断言写法转述**，不是"我跑出来 PASS 了"。我本次直接核对过的真实产物只有两个：`data/logs/monitor_selftest.csv`（逐行读完）与 `data/logs/host_scenario_A.csv`（核对了表头、首行与总行数）。`build/host/tea_picking_robot_host.exe` 是**别的流程构建出来的**，我只核对了它的存在、大小与时间戳，**没有运行它**。

### 2. 为什么这条规则是在保护候选人

校园招聘的技术面，以及 FAE 岗位的客户现场，**最常见也最致命的失分点，就是把"设计目标"说成"实测结果"**。

面试官的追问路径是固定的三步，而且只用三步：

1. "这个数字是怎么测的？"（测试方法）
2. "测了多少个样本？"（样本量）
3. "数据文件在哪儿，能打开看一下吗？"（原始证据）

三问之内答不上来，候选人失去的不是这一个数字，而是**简历上所有其他数字的可信度**——面试官会合理推断：凡是无法当场证明的，都是编的。这个损失是不可逆的，因为后续每一个回答都会被默认打折扣。大约 30 秒，就足够把一份本来扎实的简历变成一份不可信的简历。

对 FAE 岗位而言后果更重：客户现场说"我们的力控精度是 ±0.1 N"，客户下一句就是"那你们有测试报告吗"。硬件类客户对"拿不出数据"的容忍度极低，因为它直接关系到产线停机和赔偿。**一句诚实的"这是我们的设计目标，标定报告还没有，我们计划这样验证"，在客户那里的评价高于十个漂亮但站不住的数字。**

这个项目恰恰有大量**真实、扎实、可核对**的内容（18629 行一方固件源码、72 个文件、12 条编译期静态断言、49 条状态机转移、7 项上位机验收检查、7 个仿真场景）。它们不需要任何夸大就足够有说服力。**用假数字去覆盖真东西，是这笔交易里最亏的一种。**

### 3. 被追问"这个数据有吗？"时的标准答法模板

一句话结构：**先说真实性 → 再说证据边界 → 最后说验证计划。** 不要道歉，不要含糊，不要补一个更大的数字。

> "这个数字目前是**设计目标**，不是实测——我们有推导过程和源码里的阈值定义，但还没有实物板卡上的标定数据。证据边界是：目前已实现的是模型内的仿真验证和上位机自动化验收；下一步的验证计划是打板后用标准砝码做零点与量程标定，再采 N 个真实茶芽样本统计。"

三个可直接套用的实例：

- 被问抓取力 2.2 N → "这是 `config.h` 里的**设计指标**（`TP_FORCE_TARGET_N`），依据是硬限 5.0 N 与软限 3.5 N 的序关系；它在源码里有编译期静态断言保护，但**没有在真实茶芽上标定过**。计划先做砝码标定，再按品种、含水率分组统计。"
- 被问跟踪误差/效率 → "我们目前在模型里跑通了场景 A–G 并记录 max/RMS 位置误差等指标，这是**仿真结果**；真机效率和破损率**都还没有数据**，对外只能说设计目标。"
- 被问力控精度 → "±0.10 N 是代码里的**判据带**（力误差进带并连续保持 80 ms 才认为抓稳），它是"判定逻辑"，不是"精度实测值"；精度要靠标定后的重复性测试来给。"

**永远不要把"代码里的阈值"说成"实测精度"。** 阈值是设计者挑的，精度是测出来的，二者之间隔着一次完整的标定。

## 4. 嵌入式软件工程师版本

**项目名称**：第二代采茶机器人机载固件（Tea-Picking Robot Firmware, v2.0.0）
**角色**：〈嵌入式软件工程师 / 固件与工具链〉
**时间**：〈20XX.XX – 20XX.XX〉
**技术栈**（只列仓库可核实项）：
- MCU：STM32F407VET6（依据 CMSIS 器件头 `stm32f407xx.h`、启动文件 `startup_stm32f407xx.s`、链接脚本 `STM32F407VET6_FLASH.ld`）
- 语言：C（`compiler.h` 为 pre-C11 编译器保留 `_Static_assert` 的 typedef 回退，说明源码被期望在 C99 下也可编译）
- 工具链：`gcc`（host）与 `arm-none-eabi-gcc`（目标）——`compiler.h` 文件头明文列出；**仓库无 CMake/Makefile，构建流程本身未入库**

### 成就要点（STAR，Result 已按证据边界标注）

**1. 用"单一硬件接缝"换取了无板卡条件下的可测性**
S：目标板尚未打样，但控制层必须能被验证。
T：让同一份 `pid.c` / `motor.c` / `robot_fsm.c` 既能在 MCU 上跑，也能在 PC 上对着物理模型跑。
A：把全部寄存器/GPIO/总线访问收敛到 `platform_api.h` 一个编译期接缝（`-DTP_PLATFORM_HOST` 或 `-DTP_PLATFORM_STM32F407`），驱动层之上承担全部单位换算、限幅、标定与故障检测；host 侧接 `plant_model.h` 的确定性物理模型（真实惯量、库仑摩擦、量化编码器、非线性茶梗刚度）。
R：**【已实现】** host 后端、物理模型与 PC 入口（`main_host.c` 含 `main()`）完整在库，且 `build/host/tea_picking_robot_host.exe` 有真实运行轨迹 `data/logs/host_scenario_A.csv`（约 5021 行）——这使得"固件在模型里真跑起来过"是可核对的；真机后端 `platform_stm32f407.c`（约 105 KB）与机载入口 `main_stm32.c` 也已在库（见 §声明5 的时效性更正）。**【未实现／未验证】** 仍无 CMake/Makefile，机载侧无法一键构建；真机后端**从未编译、从未在实物上运行**——**"已在 STM32 上验证"这句话不能说**，只能说"代码已就绪、待板验证"。

**2. 独立完成四个 BSP 驱动，并把保护逻辑做成驱动层的不变量**
S：驱动器是唯一允许命令电机的层，必须在控制环出错时仍能自我保护。
T：把限幅、折返、锁存、标定做成驱动层不变量，而不是指望上层不犯错。
A：电机驱动实现斜率限制（4000 千分比/秒）、按电流比例折返（含 5% 下限，避免单次噪声把驱动降到零）与 20 个连续超限样本触发的过流锁存；编码器实现 4 倍频计数、基于累计窗的速度估计，并在方向反转时重置滑动平均（否则 +v 与 −v 平均出近零速度，会骗过堵转检测）；称重通道实现中值(5)→滑动平均(8)→一阶低通(τ=6 ms)三级滤波与尖峰检测；夹爪实现 3 s 超时回零与"限位否决作用在速度上而非占空比上"。
R：**【已实现】** 四个驱动均在库；`-TP_MAX_PWM_PERMILLE`、`TP_MAX_CURRENT_MA`、`TP_STALL_PWM_THRESHOLD` 等阈值全部来自 `config.h`，驱动里不写魔数。

**3. 协议栈：流式解析器 + 两条标准总线**
S：UART 只交付字节流，既不能假设"一次读到一个完整帧"，也不能让解析器在噪声后永久失步。
T：做出对截断帧、噪声、误头都正确的解析器，并对接 PLC 与多节点总线。
A：7 状态机逐个字节解析 `AA 55 CMD LEN PAYLOAD CRC16`；重同步时把"第二个字节不是 55"重新当作可能的 `AA`（因此 `AA AA 55` 不会丢帧）；长度字节在分配前先校验；CRC 失败后从假头之后继续搜索而不是吞掉整个候选帧；CRC-16/MODBUS 采用位运算实现（校验值 `0x4B37`），并在注释中写明"何时才该改成查表"。同时实现 Modbus RTU 从站（4 个功能码、4 个异常码、DE 方向状态机 + 304 µs 帧间静默）与 CAN 2.0A 500 kbit/s（3 邮箱、4 个验收滤波器、TEC/REC/bus-off 跟踪）。
R：**【已实现】** 协议自检（CRC 校验向量 + 往返编解码）作为 `host/selftest.py` 第 1 项检查真实存在。

**4. 让配置错误在编译期失败**
S：可调参数集中在一个头文件里，错误的组合（如可用量程覆盖不了硬力限）一旦漏到运行时就是硬件损坏。
T：把关键不变量变成构建失败。
A：在 `config.h` 末尾布置 **12 条** `TP_STATIC_ASSERT`：五个任务速率必须整除 1 kHz 控制率、控制率不能高到周期不足 1 ms、力目标 < 软限 < 硬限、位置环输出钳位必须容得下关节最大速度、帧长上限不得超出 RX 环形缓冲、模拟前端在额定负载下不得超参考电压、可用力量程必须覆盖硬力限。
R：**【已实现】** 12 条断言在库、可逐条核对；错误配置会直接编译失败，而不是在运行中表现为"关节冲过软限"。

**5. 上位机工具与自动化验收**
S：没有实机，验收标准就必须落到可执行的检查上，否则"跑通了"只是一句话。
T：把 PC 侧工具做成可一键验收的套件。
A：`host/selftest.py` 以真实子进程方式运行 7 项检查：协议编解码自检、视觉模拟器打印 20 帧十六进制、视觉模拟器 20% 丢包确实丢、监控工具无头跑完一次采摘演示序列、CSV 落盘后交给日志分析工具、分析工具自检、以及"tkinter 故意坏掉时仍能 import 监控模块"；只有 7/7 通过才返回 0。
R：**【已实现｜可复现】** 检查脚本与真实产物 `data/logs/monitor_selftest.csv`（表头 + 66 行数据）均在库。**注意诚实边界**：该 CSV 记录的是 3 秒无头演示，`state` 只从 0→1→2 停在 IDLE，位置/速度/力/占空比全为 0——它**不能**当作"完成了一次采摘"的遥测证据；完成采摘循环的证据是第 4 项检查在脚本内断言的 `sim cycle count ≥ 1` 与 11 步演示序列。

**6. 分层、可测性与资源约束**
S：1 kHz 控制环最怕隐式开销和"某处偷偷分配内存"。
T：让每个模块都能脱离硬件被单独调用。
A：统一返回码 `tp_status_t`（15 个错误码，全负值，`< 0` 即失败）；全工程无动态分配，环形缓冲以调用方持有的存储初始化（容量向下取 2 的幂以便用掩码替代除法）；日志层的时间源与输出汇均可注入（因此可断言到具体一行日志）；FreeRTOS 与裸机两套 OSAL 后端实现同一接口。
R：**【已实现】** 架构与代码在库；7 个任务体已实现于 `app_sequence.c`，任务创建/启动在 `app_tasks.c`，PC 入口 `main_host.c` 已就绪。**【未实现】** 机载入口 `main_stm32.c` 与全部构建脚本缺失（无 CMake/Makefile），**无法从仓库一键构建**；`tests/` 与 `firmware/Tests/` 均为空，没有任何测试文件——"可测性"是架构属性，不是既成事实。

### 可能的追问（3–5 条）

1. **为什么用单一编译期接缝，而不是每个驱动一个函数指针 vtable？**
   → 接缝是**编译期**的：1 kHz 环里没有间接调用，编译器能把 `tp_platform_motor_set_pwm` 内联到一次寄存器写入，`--gc-sections` 能删掉目标平台用不到的代码，而且"谁碰了硬件"只有一个文件的答案。vtable 的价值在于同一产品出货两种可互换传感器——本项目传感器是固定的。**但要注意：这是设计说明，不是性能实测，我没有测过内联前后的周期数。**

2. **host 后端和真机后端怎么保证行为一致？**
   → host 侧刻意把内部连续角度**量化到与真实硬件相同的计数栅格**，所以量化效应在仿真里也出现；物理模型含真实惯量、库仑摩擦与电流限幅，不是返回零的桩。边界是：一致性只在"模型写了什么"的范围内成立，真机后端尚未实现，所以**谈不上"已对齐实测"**。

3. **CRC 为什么用位运算不用查表？**
   → 921600 baud 最坏约 92 kB/s，位运算约 736k 次内层迭代/秒，远低于 168 MHz Cortex-M4 的 1%；512 字节查表能再降一个量级，但要吃掉 512 字节 flash 而永远用不上。注释里写明了重新评估的条件（持续流量升到约 5 Mbaud 以上，或 CPU 预算收紧）。**这是设计权衡，不是实测数据。**

4. **环形缓冲满了丢新字节还是覆盖旧字节？为什么？**
   → 丢新字节并累加溢出计数。对命令链路，丢一个截断帧的尾巴是无害的——解析器会在下一个 `AA 55` 重同步；覆盖旧数据反而会污染一个已经部分接收的合法帧。同时维护 occupancy 高水位，让"缓冲该开多大"有数据可依，而不是靠猜。

5. **没有任何单元测试文件，你凭什么说驱动层逻辑正确？**
   → 必须承认：**目前没有可运行的单元测试，`tests/` 为空，我不声称"逻辑已验证"**。我能说的是架构为测试做的准备：驱动层承担全部可测行为（换算/限幅/标定/故障）、注入式日志时间源与输出汇、`tp_limit_switch_force()` 这类仅供测试注入的入口、以及 host 物理模型让整机能在 PC 上跑。下一步计划是把 PID、帧解析、环形缓冲、限流状态机补成表驱动测试——这也是我下一步就在做的事。

## 5. FAE 版本

**项目名称**：第二代采茶机器人机载固件与上位机工具链（v2.0.0）
**角色**：〈固件开发 / 现场调试与客户支持〉
**时间**：〈20XX.XX – 20XX.XX〉
**技术栈**：C / STM32F407VET6 / FreeRTOS(CMSIS-RTOS2)；帧协议（CRC-16/MODBUS）与 Modbus RTU 从站、CAN 2.0A；Python 3 上位机工具（监控、日志分析、视觉模拟、自动化验收）。

### 成就要点

**1. 分层定位法：把"现象"先映射到"层"，再动手**
S：没有实物时，任何现场问题都只能是"描述 → 定位"。
T：建立一套不依赖猜测的定位顺序。
A：把可观测面按层切开——安全层的故障登记表把"现在是否为真 / 是否已锁存 / 一共发生过几次"分成三个独立的问题；安全监视器把八类检查按各自的时间常数分开（过力与急停**不去抖**，堵转 300 ms、过流 50 ms 去抖）；协议层把错误按类型分开计数。于是"客户说偶尔不动"可以按 故障码 → 检查项 → 层内计数器 逐层收窄。
R：**【已实现】** 三个问题分开登记、按检查项去抖、"绝不对保护对象（茶芽、人）做去抖、只对保护机器自身的检查去抖"的非对称原则均写在代码与注释里。

**2. 可观测性设计：日志格式固定，且"被压掉多少条"必须可见**
S：一个每毫秒都会触发的故障会淹没链路，把最重要的**首次**记录冲掉。
T：限流，但绝不隐藏限流这个事实。
A：日志格式固定为 `[时间][模块][级别] 消息`，模块标签集中定义（CONTROL / SAFETY / GRIPPER / MOTOR / PROTO…）便于 grep；输出汇与时间源都可注入（因此可以断言到具体日志行）；**限流同时提供被抑制条数与被发出条数**两个计数器，任何"日志怎么少了"的疑问都有数字回答。
R：**【已实现】** 日志 API 与限流计数接口在库。

**3. 可复现性与根因分析：每类错误分开计数**
S："坏帧计数"这种笼统指标对定位毫无帮助——CRC 失败、长度非法、失步指向完全不同的根因。
T：让每个计数器指向一个可行动的假设。
A：帧解析器分别计数 CRC 错误、长度非法、重同步次数与被丢弃字节数（前者指向干扰或波特率不符，中者指向成帧问题或版本不匹配，后者指向**上游截断**）；RS485 侧另计冲突次数、方向切换次数、CRC 错误与超时；UART 侧单独暴露接收溢出与占用水位高水位——溢出在涨，就说明消费太慢或缓冲太小，最后都会被误报成"神秘的 CRC 错误"；CAN 侧跟踪发送重试、丢弃、被滤波器过滤、TEC/REC 与 bus-off。
R：**【已实现】** 上述计数器均在各模块结构体中定义并维护。

**4. 故障码分级，且把"码"翻译成"客户能懂的话"**
S：客户现场需要的是"现在能不能继续、下一步按什么"，不是十六进制。
T：让故障码自带严重度与处置说明。
A：11 个故障码配 4 级严重度：INFO 仅记录；WARNING 记录 + 遥测置位、运动可继续（如通信超时、限位）；ERROR 停止运动、须在条件消失后清除（如过流、堵转）；CRITICAL 直接**硬件杀 PWM**并需复位（如急停、编码器反馈不可信）。同时提供"恢复建议"接口，把码转成给操作员的一行指令；故障的 detail 字段携带量值（过力用厘牛、过流用百毫安、堵转用十千分比占空比），这样客户问"有多严重"时能直接给数。
R：**【已实现】** 严重度表、分级反应、恢复提示接口与 detail 编码均在库。

**5. 保护"不可被绕过"的一致性**
S：如果清除故障的接口在条件未消失时也放行，操作员连按两次就能把保护关掉。
T：让所有清除路径口径一致。
A：电机驱动、力控状态机、故障登记表三处都实现了同一原则——**条件仍然为真时拒绝清除**；急停输入采用常闭回路，因此**断线也读作急停**（失效安全极性），并且这一路**不做去抖**，因为它的全部价值就在于即时。
R：**【已实现】** 三处拒绝清除的逻辑与常闭回路极性处理均在库。

**6. 跨团队接口：给视觉留位置，给 PLC 留标准**
S：机器人不是孤立设备——上接视觉系统，下接产线 PLC。
T：自定义协议只用在标准不存在的地方。
A：自研帧协议承载机器人专有数据（目标坐标 + 置信度 0–100 + `target_id`，使机器人日志能和视觉日志按 ID 关联而不必靠时间戳对齐）；同时实现 **Modbus RTU 从站**，把位置、力、状态、故障映射成普通保持寄存器，任何 Modbus 主站都能读——**在已有标准的地方实现标准，只在没有标准的地方自定义**。接口文档中明确写出小端约定，因为"把 2.0 N 读成 8192 N"就是小端/大端误解的典型后果。
R：**【已实现】** 协议、从站功能码、寄存器访问路径在库；**【缺失】** 源码引用的寄存器映射文档 `docs/07_communication_protocol.md` 不在仓库，交付前必须补齐——否则"有文档"这句话就是空的。

### 可能的追问（3–5 条）

1. **客户说"偶尔丢一帧"，你怎么三步定位？**
   → 第一步看**类型**（CRC 错 / 长度非法 / 失步 / 接收溢出，各指向不同根因）；若接收溢出在涨就是本地消费太慢或缓冲偏小，若全是 CRC 错就查波特率与接地/屏蔽；第二步看**时间相关性**（是否总在电机大电流动作时出现，那更像 PWM 干扰耦合）；第三步才动硬件（缩短线缆、加终端匹配、改走 CAN）。**我没有现场数据，这是方法论不是战果。**

2. **Modbus 从站支持哪些功能码？异常码怎么定义的？**
   → 读保持寄存器 0x03、读输入寄存器 0x04、写单个 0x06、写多个 0x10；异常码为非法功能 0x01、非法地址 0x02、非法数值 0x03、从站故障 0x04。地址 0（广播）与大于 247 的地址在初始化时就被拒绝。

3. **故障码 detail 只有一个字节，够用吗？**
   → 够用于"量级提示"，不够用于"精确数值"。现在按量纲缩放（过力用厘牛、过流用百毫安、堵转用十千分比占空比）能覆盖现场判断；要精确值就走遥测帧里对应的整数字段。这是接口取舍，我在文档里写明了。

4. **为什么 E-stop 不做去抖？抖动会造成误停吗？**
   → 常闭回路的抖动最坏结果是短暂停一次；而不去抖换来的是"断线 = 立即停机"。**保护对象和操作员的检查不做去抖，保护机器自身的检查才做**——误停是麻烦，漏停是事故。这个取舍是刻意写在代码注释里的。

5. **如果客户 PLC 是大端，或者寄存器地址从 1 开始编，你怎么处理？**
   → 我们的帧协议与 Modbus 寄存器内容都按小端/标准 Modbus 地址（0 基）实现，并在对接文档里写死；如果对方约定不同，就在网关侧或从站映射层做一次显式转换，**不在协议实现里偷偷兼容两种**，因为隐式兼容会让下一个人无法调试。

## 6. 机器人控制工程师版本

**项目名称**：第二代采茶机器人控制层（串级 PID + 力控柔性夹持，固件 v2.0.0）
**角色**：〈运动控制 / 机器人控制算法与实现〉
**时间**：〈20XX.XX – 20XX.XX〉
**技术栈**：C（1 kHz 实时控制环）/ STM32F407VET6 / FreeRTOS；串级 PID、轨迹生成（梯形与 S 型）、力闭环柔性夹持；Python 仿真器（7 场景 A–G + 物理模型）。

### 成就要点

**1. 串级（位置→速度）结构及其带宽约束**
S：单环位置 PID 的增益同时决定响应速度与阻尼，两者方向相反——为提高响应加大增益就会压缩相位裕度直到振荡。
T：把"设阻尼"和"设响应"交给两个环。
A：位置环 `Kp = 12.0`、`Ki = 0.5`，输出**速度参考**，钳位 ±40000 mrad/s（= 关节最大速度），积分钳位 ±8000（**刻意远小于输出钳位**）；速度环 `Kp = 0.015`、`Ki = 0.30`，输出 **PWM 千分比**，钳位 ±1000，积分钳位 ±400。内环先初始化（其输出范围就是驱动范围），外环的输出限幅写成"内环的输入范围"，把设计意图编码进一行赋值。并且明确写出**什么时候不该串级**：内环带宽做不到外环的 3 倍以上时，串级反而更差。
R：**【已实现】** 两个环、限幅关系、模式切换（OFF / 仅速度 / 全串级）与切换时**双积分器清零**均在库。**【设计目标】** 注释中给出速度环 ≈8 Hz、位置环 ≈0.55 Hz、约 15× 分离——**其推导文档不在仓库，我无法独立复核这两个数字**。

**2. 两套抗积分饱和，各有明确适用面**
S：饱和期间执行器跟不上控制器，继续积分就是纯粹的虚构，会导致"先猛冲、再花几秒退回来"。
T：同时提供平滑与低成本两种方案。
A：**反算（back-calculation）**把饱和误差通过跟踪增益反馈回积分器，跟踪时间常数取 `Tt = Kp/Ki`（由增益自动推导，也使积分器按与绕上相同的时标绕回），并**把单次修正限制在一个钳位宽度内**，免得巨大的饱和误差把积分器甩到对面轨；**条件积分**只在"输出已饱和且误差仍朝同方向推"时冻结本步积分（若只判饱和而不判方向，积分器将永远退不出来）。另有两条不变量：积分钳位不得超过输出钳位；积分增益为负时直接拒绝配置（否则抗饱和反馈会变成正反馈）。
R：**【已实现】** 两套策略与不变量校验均在库，策略可由 `config.h` 选择（当前默认反算）。

**3. 微分项的三处工程处理**
S：对误差求微分会在设定值跳变时产生冲激（微分冲击），电机忠实地把它变成电流尖峰；而 1 kHz 下原始差分几乎全是编码器量化噪声。
T：让 D 项贡献阻尼而不贡献噪声和冲击。
A：**微分作用在测量值上**（对 y 求导而非对 e 求导），设定值跳变不再产生冲激；**微分低通**用后向欧拉离散化 `alpha = dt/(τ + dt)`，保证 `dt > τ` 时依然稳定（教科书的 `dt/τ` 会发散）；**积分用梯形法**而非矩形法，消除斜坡误差下 I 项的系统性半样本偏差（表现为永久的小稳态位置偏移）。三项各自的作用与"没有它会怎样"都写在头文件的对照表里。
R：**【已实现】** 三处处理均在 `pid.c` 中实现并可逐行核对。

**4. 轨迹发生器 + 速度前馈**
S：把阶跃直接交给位置环，等于要求一个物理上不可达的参考——内环饱和、积分器绕上、关节过冲，然后人们去怪增益。
T：让参考本身先满足机器的速度与加速度约束。
A：实现 STEP（仅测试用，用于刻画环路）、梯形（采摘默认）、S 型（加加速度受限，用于末端接近以免晃动茶芽）三种 profile；**时长由限幅反推而不是由调用方给定**（避免操作员要求机器做不到的移动，而那正是发生器存在的理由）；发生器是**时间的纯函数、不含积分器**，所以暂停或改速率不会污染状态。其速度输出直接作为前馈，并且**前馈加在内环的参考上而不是内环的输出上**——加到输出会绕过限速器，加到参考上则限速仍然有效、前馈永远可达。
R：**【已实现】** 三种 profile、时长反推、前馈路由与限幅校验均在库。

**5. 力控柔性夹持：六段状态机 + 分级保护**
S：茶芽的刚度随品种、含水率、芽龄变化，机器人无法预先知道；按**位置**闭合到固定间隙，在比预期更硬的茎上会沿二次刚度曲线上冲，在控制器拿到任何信息之前就已经压坏。
T：改为按**力**闭合。
A：`FAST_APPROACH`（40 mm/s，到预期接触点前 4 mm 就减速，以便接触发生时已建立控制权限）→ `SLOW_APPROACH`（6 mm/s）→ `CONTACT_DETECT`（要求力连续 3 个样本高于 0.15 N 才算接触；力若回落到阈值一半则退回慢接近）→ `FORCE_CONTROL`（力 PID `Kp=14 / Ki=6 / Kd=0.05`，输出**夹爪速度**，钳位 ±25 mm/s——刻意远小于机械极限 120 mm/s，否则接触后第一个采样就会命令出足以损伤茶芽的力阶跃；力误差进入 ±0.10 N 带**并连续保持 80 ms** 才算抓稳，中途出带则计时重来）→ `PICK`（继续保持力并加 2.0 mm/s 补压，防芽滑脱）→ `RELEASE`（30 mm/s 开爪）。保护按优先级执行：**硬限 5.0 N 在控制器之前判定**，当周期即开爪并锁存；软限 3.5 N 不跳闸而是把设定值降到 3.15 N 让环路主动退让；传感器故障直接放弃力控；接触超时 2.5 s 则中止（说明芽不在视觉所说的位置），而不是一直合到机械死点。
R：**【已实现】** 状态机、保护优先级、去抖与统计量（保持段样本数、平均/最小/最大保持力、峰值力、过力次数、超时次数）均在库。**【设计目标·未验证】** 2.2 N 设定、自适应阈值（EMA α=0.05、余量 0.60 N）——自适应**尚未在真实茶芽上验证**；且头文件称其"默认关闭"而 `config.h` 实际默认开启，**这一矛盾必须先澄清再对外表述**。

**6. 实验设计与指标量化**
S：没有指标的实验只是演示，"力控更好"不能靠感觉。
T：把结论做成可复现的运行 + 可比较的指标。
A：设计 7 个仿真场景——A 正常采摘、B 视觉目标误差（横向 8 mm + 深度 5 mm，按 300 mm 工作半径折算成关节偏移）、C 力噪声 0.08 N（**并跑一条同种子、只关掉滤波的对照臂**，把"滤波有用"从主张变成对比）、D 过力目标 4.5 N、E 300 ms 断链、F 30 N·m 卡死、G 1.2 s 急停；批量运行中单个场景异常不会掩盖其余六个的结果。指标侧在控制器内累积：最大位置误差、**增量式均方误差**（不存整段历史即可报 RMS）、位置误差超 5° 的周期数、内/外环饱和周期数；力控侧输出平均保持力与峰值力。
R：**【已实现】** 控制器内统计与 7 场景代码均在库。**【仿真】** 所有数值只可能是仿真结果；**本次未复算**，也不存在多种子重复统计（固定种子单次运行）。

### 可能的追问（3–5 条）

1. **为什么速度环带宽要做到位置环的 10–20 倍？**
   → 串级的前提是内环足够快，使外环看到被控对象近似为一个纯积分器（`θ' = v_cmd`），这样外环只需按一阶模型整定。一般要求 3–5 倍以上；我们按 10–20 倍先定比例再整定内环，最后才整定外环——**"先定比例、再调内环、最后调外环"是设计约束而不是调参结果**。但 8 Hz / 0.55 Hz 这两个具体数值的推导文档不在仓库，我只能说明方法，不能出示推导。

2. **反算抗饱和的跟踪增益为什么取 `Kp/Ki`？**
   → 取 `Tt = Ti = Kp/Ki` 使积分器**按与绕上相同的时标绕回**，这是经典选择；代码里允许显式覆盖，并在 `Ki` 或 `Kp` 近零时退化为"积分器永久自由"（因为没有积分作用就没有饱和可谈）。

3. **力 PID 的输出为什么限制在 25 mm/s，而机械极限是 120 mm/s？**
   → 因为力环的输出是**速度指令**：接触后第一个采样若允许全速闭合，产生的力阶跃在环路能反应之前就超过损伤阈值。25 mm/s 是"保证环路来得及"的约束，不是机构能力的约束。**这个 25 是设计取值，不是整定出来的最优值——真机上需要重新标定。**

4. **力信号已经过中值→滑动平均→低通三级滤波，力 PID 的 D 项还有意义吗？**
   → 有意义但收益变小：滤波削掉的高频正是 D 项最想放大的部分，而 D 项在这里主要提供接触瞬间的阻尼。`Kd = 0.05` 相对 `Kp = 14` 很小，且微分低通时间常数取 10 ms。**诚实的说法是：这一项在仿真里的贡献尚未做消融实验，我不能说它一定必要。**

5. **这些增益是怎么来的？仿真里 `Kt = 0.4 N·m/A`、`J = 2.5e-3 kg·m²`、`k1 = 0.30 N/mm` 又是哪来的？**
   → 增益是**设计起点值**，写在 `config.h` 里作为默认值，并支持运行期通过 `SET_PID` 命令在线改（正是为了让扫参实验不必重新烧写）；机械参数是**模型假设值**，不是实测辨识值——仿真里也没有做过参数辨识实验，所以"仿真吻合真机"这句话目前**没有依据**，只能说"模型内自洽"。

## 7. 硬件 / 嵌入式联调版本

> **本节全部内容为设计计算与设计推理，尚无实物板卡、无任何测量数据。** 下面每一条都请当作"我打算这样做，并且我能把算式讲清楚"，而不是"我测出来是这样"。
> （仓库中的 `hardware/motor_driver.md` 独立给出了同一条 12 A 推理，并在文件开头自行声明"没有任何实物板卡被制造过，也没有任何板卡被测量过"——两条来源互相印证，口径一致。）

**项目名称**：第二代采茶机器人硬件前端设计与嵌入式联调（设计阶段，v2.0.0）
**角色**：〈硬件/固件联调〉
**时间**：〈20XX.XX – 20XX.XX〉
**技术栈**：STM32F407VET6（12 位 ADC + 循环 DMA、TIM 正交编码、TIM PWM、USART、CAN1）；INA333 仪表放大器 + 称重传感器前端；24 V 母线驱动；RS485/Modbus RTU 与 CAN 2.0A 接口。

### 成就要点

**1. 模拟前端设计：由测量需求反推器件，而不是反过来**
S：抓取力目标 2.2 N、硬限 5.0 N，因此读数分辨率必须远好于 20 mN。
T：让电子学的复杂度尽可能低，同时把量程与分辨率都锁进编译期。
A：选 **10 N / 1 mV/V / 5 V 激励** 的称重传感器 → 桥路输出 **0.5 mV/N**；**INA333 取增益 201（RG ≈ 249 Ω）** → 前端 **100.5 mV/N**；12 位 ADC、3.3 V 基准 → 单步 **0.806 mV**，于是 **LSB = 8.0 mN**。校核余量：额定 10 N 时输出 **1005 mV**，远低于 3.3 V；ADC 在 **32.8 N** 才饱和，远高于 5 N 硬限——**过载由固件判定，而不是悄悄贴轨**。选 10 N 而不是 50 N 是刻意的：50 N 单元只有 0.1 mV/N，需要增益 400，届时放大器自身失调漂移与桥路温漂会成为主导误差；**"让传感器迁就电子学"比"把微弱信号放大 400 倍"是更好的工程答案**。所有这一步的数值**全部由 `config.h` 的宏导出**（`TP_LOADCELL_*`、`TP_FORCE_AMP_GAIN`、`TP_ADC_MV_PER_COUNT`、`TP_FORCE_CAL_SCALE_N_PER_COUNT`），改一个常量会一致地传导，驱动里不留手写魔数；两条静态断言在"前端超额"或"量程不足"时直接**编译失败**。
R：**【设计计算】** 全部数字为参考设计与算式推导（`config.h` 注释中明确写明"derived from datasheet figures, not measurements taken on a built board"）。**注意：仓库另有 `simulator/config.py` 使用 50 N 单元 / 增益 128 / 0.0012 N per count，`filters.h` 又写"约 12 mN"——三处不一致，报出去之前必须先统一。**

**2. ADC 走循环 DMA 的三条理由**
S：5 个模拟通道（力、两路电流、母线电压、备用），采样任务 500 Hz。
T：让采样点稳定、通道间一致、且不占用 1 kHz 控制任务的 CPU。
A：**（1）抖动**——轮询的采样时刻取决于任务何时被调度；定时器触发的循环 DMA 把采样点锁在硬件定时器上，因此**等间隔**，而速度估计要除以时间、力控要微分，两者都对抖动极其敏感。**（2）相干性**——一个 DMA 块在数微秒内取完全部通道，因此同一记录里的力与电流确实属于同一瞬间；轮询则可能相隔一毫秒，二者之间的相关性分析随之失去意义。**（3）CPU**——搬运零周期开销。缓冲刻意做小（16 样本/通道，500 Hz 下约 32 ms 余量，够覆盖一个 tick 加一次 flash 擦写级别的抖动），并配**溢出计数器**，把"错过截止期"变成可见数据而不是静默的数据损坏；另提供抽取平均（4 抽样→500 Hz）在不增加相位滞后的前提下多 6 dB 抑噪。
R：**【设计计算／设计推理】** `adc_driver.h` 中三条理由与缓冲权衡均成文；驱动实现【已实现】。**注意**：`config.h` 的 `TP_ADC_DMA_BUFFER_LEN = 16` 实际无人引用，驱动用的是自己的 `TP_ADC_BLOCK_MAX = 32`。

**3. 信号调理：三级数字滤波，各解决一类噪声**
S：12 位 ADC 在 1 mV/V 传感器上给出的原始信号"阶梯感"明显；PWM 载波会耦合进称重线；还会有孤立的坏采样。
T：每一类噪声用对的工具，而不是一个滤波器打天下。
A：**中值(5)** 消除孤立尖峰（滑动平均与低通只会把尖峰摊到整个窗口，反而是中值能彻底剔除，所以放在**最前**）；**滑动平均(8)** 抑制宽带/量化噪声，且是**线性相位**，不会扭曲接触瞬变的形状；**一阶低通 τ = 6 ms（≈26.5 Hz）** 提供可预期的 −20 dB/十倍频滚降，且只有一个状态量、便于在 1 kHz 环里推理。三者的缺失后果都写明：没有中值→单个坏样本变成数百毫牛的力毛刺，会被力环当成接触事件；没有滑动平均→力 PID 的 D 项把量化噪声放大成 PWM 抖动，白白加热夹爪伺服；没有低通→20 kHz 载波混叠进控制带，与真实力无法区分。
R：**【已实现】** 三个滤波器均为无动态分配、可复位、按实例可重入的实现。**【设计计算】** "8.0 mN LSB 因此需要三级滤波"这一因果链是设计推理，**不是噪声实测**。

**4. 信号保护与合理性检查**
S：传感器断线、贴轨、以及"信号在动"时的错误标定，都会产生看起来合法的错误读数。
T：让坏数据在被用之前就被拒绝，并区分"坏一次"和"坏透了"。
A：**尖峰检测**（跳变超过 1.0 N 视为不可能，连续 8 次则判定通道故障）、**饱和/贴轨检测**（计数为 0 或 ≥ 4095）、**量程窗口检查**（力 −20…50 N、原始计数 5…4090）、**零点标定拒绝**（极差超过阈值即拒绝，因为"对还在动的信号取平均"会得到一个偏了运动均值的零点，之后每个读数都继承这个错误）、**标定比例合理性**（与设计值相差 10 倍即拒绝，避免解出一个毫无意义的巨大比例因子）。
R：**【已实现】** 全部检查与拒绝路径均在 `force_sensor.c` 中实现。

**5. 电源与电气约束推理**
S：控制环的输出可以在两个采样之间跳满 1000 千分比。
T：说明为什么占空比必须被限制变化率，而不只是限制幅值。
A：24 V 母线（由 ADC 经 10:1 分压监测）；连续电流限 3000 mA、短时（<50 ms）峰值 5000 mA。若占空比阶跃到 100%，电流**只受绕组电阻限制**：以模型中 R = 2 Ω 计，`24 V ÷ 2 Ω ≈ 12 A`，约为连续限的 **4 倍**，足以触发驱动器过流保护、在廉价板上甚至击穿 FET。因此 `TP_MAX_DUTY_RATE_PER_S = 200000 千分比/秒` 把阶跃变成受控斜坡——**斜率是一个写在 `config.h` 里的设计参数，而不是环路时序的副产物**。另外过流时按电流比例折返占空比，并保留 **5% 下限**，避免单次噪声采样把驱动直接折到零；驱动层在连续 20 个超限样本（1 kHz 下 20 ms）时锁存过流，安全层则在 50 ms 量级提升为故障——**两层保护用不同的时间常数，是有意的分工**。
R：**【设计计算】** 12 A 与斜坡论证来自 `motor.h` 注释与模型参数推算，**无示波器实测**。

**6. 接口的电气时序与失效安全极性**
S：半双工 RS485 的方向控制、多节点 CAN 的故障隔离、以及安全回路，都是"接通了不等于正确"的地方。
T：把每种接口最容易在长线多节点时才暴露的坑写在代码里。
A：**RS485**——必须在第一个起始位之前拉高 DE，并且必须等到**最后一个停止位物理离开移位寄存器之后**（传输完成 + 20 µs 保护时间）才释放 DE：用"发送寄存器空"中断释放是经典 bug，寄存器空了而移位寄存器没空，末字节会被截断；帧边界按 Modbus RTU 规定的 3.5 字符静默（115200 下 304 µs）实现，而不是"取个 1 ms 觉得安全"。**CAN**——500 kbit/s，选它的价值不是速度（比 UART 慢）而是**仲裁与错误隔离**：多节点共用两线、标识符即优先级、坏节点被控制器的错误计数器隔离；驱动显式返回"邮箱全忙"让调用方下个周期重试，而不是阻塞。**E-stop**——常闭回路，**断线即急停**；限位开关是上拉到地的常开型，**未插即未触发**，两种极性**相反**，因此极性作为显式参数传入而不是藏在一个布尔量后面。
R：**【已实现】** DE 方向状态机、静默窗口、CAN 邮箱与滤波器管理、极性参数化均在库。

### 可能的追问（3–5 条）

1. **INA333 的 RG 怎么算出 249 Ω 的？**
   → INA333 的增益关系为 `G = 1 + 100 kΩ / RG`，取 G = 201 解得 RG ≈ 249 Ω（`config.h` 注释中写明该值与来源）。**这是按 datasheet 公式的选型计算，我没有实测增益误差，也没做电阻容差分析。**

2. **为什么不用 50 N 传感器再放大 400 倍？**
   → 50 N / 1 mV/V 只有 0.1 mV/N，要拿到 8 mN 的 LSB 需要约 400 倍增益；此时放大器的输入失调漂移与桥路热漂移会被同样放大 400 倍并主导读数。**换传感器把电子学复杂度降下来，比把微弱信号放大 400 倍更好**——这是设计判断，不是测试结论。

3. **`config.h` 说 8.0 mN，`filters.h` 说约 12 mN，仿真里是 1.2 mN，到底哪个对？**
   → **必须承认仓库里三处不一致，在打板标定之前我给不出"哪个对"的答案。** 可核对的推理链只有一条：0.5 mV/N × 201 = 100.5 mV/N，3.3 V/4096 = 0.806 mV，故 0.806/100.5 = 8.0 mN。另外两处要么是笔误，要么对应另一套前端参数；**这也正是"必须先复算再写进简历"的典型例子。**

4. **循环 DMA 的缓冲只有 16 个样本，会不会丢数据？**
   → 16 样本/500 Hz 约 32 ms 余量，足以覆盖一个 tick 加一次 flash 擦写级别的调度抖动；而且**丢没丢是有数据的**——溢出计数器会涨，不会静默损坏。真要调大，代价是采样到消费之间的延迟变大（这个权衡写在驱动头文件里）。

5. **RS485 上如果两个节点同时驱动会怎样？**
   → 两个驱动器短接，电流只受收发器的短路保护限制——所以驱动在接收进行中直接**拒绝**进入发送（返回"忙"，要求调用方重试），并且单独统计**冲突次数**，让这种"只在长线多节点时才出现"的问题在计数上可见。物理层保护是收发器给的，逻辑层要做的是不让它发生。

## 8. 面试官最可能追问的"硬问题"清单（跨版本汇总）

1. **"力控精度是多少？"** → 说清 `±0.10 N` 是代码里的**抓稳判据带**，不是实测精度；实测精度需要标定与重复性测试，目前没有。
2. **"有没有实物？跑过吗？"** → 没有实物板卡，**没有任何硬件测量**；真机后端 `platform_stm32f407.c`（约 105 KB）与 `main_stm32.c` 源码已在库但**从未编译、从未在实物上运行**。确实跑过的只有两样，要主动说清：① PC 上的 host 仿真二进制（`build/host/tea_picking_robot_host.exe` + `data/logs/host_scenario_A.csv` 约 5021 行）；② 上位机 Python 工具的自动化验收。**如果对方追问"那 PASS 算不算验证"，标准答法是：它验证的是固件逻辑在模型下的自洽与不崩，不验证真实电机、传感器和时序——这两件事的证据类型完全不同，不能互相替代。**
3. **"这些数字是怎么测的？"** → 一律先回答来源（代码阈值 / 算式推导 / 仿真），再说明没有实测，再说验证计划。
4. **"破损率多少？"** → 仓库里**没有**这个数据；目前连损伤评定方法都未建立，只能说设计目标，并说明打算怎么测（分级力加载 + 显微/称重判据）。
5. **"效率提升了多少？"** → 仓库里**没有**对照实验、没有基线；只能给设计目标（如节拍），并说明需要同地块、同品种、同操作者的对照。
6. **"仿真结果能代表真机吗？"** → 不能。模型参数（Kt、J、k1、k2、损伤阈值 4.0 N）都是**假设值而非辨识值**，也从未与真机数据比对；模型内的结论只在模型内成立。
7. **"为什么选这个芯片？"** → 需要单精度 FPU、多路定时器（正交编码 + PWM）、12 位 ADC + DMA、CAN 与多路 UART；**这是选型理由，我没有做过功耗、BOM 或替代方案对比测算。**
8. **"PID 的增益怎么整定的？"** → 是设计起点值，写在 `config.h`，并刻意支持运行期在线改（为了扫参不必重烧）；**真机上的整定尚未开始，仿真里也没有做系统的辨识。**
9. **"有没有单元测试？覆盖率多少？"** → `tests/` 与 `firmware/Tests/` 都是空目录，**没有可运行的单元测试，我不报覆盖率**；可测性是架构属性（单一接缝、host 后端、可注入日志/时钟），下一步是把 PID、帧解析、环形缓冲补成表驱动测试。
10. **"怎么保证 host 后端和真机行为一致？"** → host 侧把角度量化到与硬件相同的计数栅格、物理模型含惯量与摩擦，**但真机后端还不存在，所以"一致"目前无法证明。**
11. **"为什么用自定义协议，不用现成的？"** → 有标准的地方就用标准（Modbus RTU 给 PLC），自定义只用在承载机器人专有数据的地方（目标坐标、`target_id`、故障码、PID 增益）；**这是取舍，不是偏好。**
12. **"限流、故障码、寄存器地址这些文档在哪？"** → 源码引用的 `docs/*.md`（含通信协议与寄存器映射）**均不在仓库**，我必须承认文档是缺口，交付前要补齐；不能拿注释当文档。
13. **"代码能构建吗？CI 呢？"** → 仓库里**没有 CMake/Makefile/SConstruct，也没有 CI**，`build/host/` 里的可执行文件是仓库外构建的产物、构建命令不在库，因此**无法从仓库一键构建**；只有链接脚本与启动文件。这是明确的工程债，我把它列在待办的第一位而不是解释成"设计如此"。
14. **"为什么 `motor.h` 说过的自清除没实现？"** → 承认 `TP_MOTOR_OC_RECOVER_MS`、`TP_SENSOR_FAULT_DEBOUNCE`、`TP_GRIPPER_BACKOFF_MM` 三处"注释写了、代码没实现"，**注释与代码不一致本身就是 bug**，应修注释或补实现，而不是在面试里解释成"设计如此"。
15. **"这个项目里你具体做了什么？"** → 只讲能打开文件的东西（分层与接缝、四个驱动、协议栈与两条总线、串级与力控、安全分级、上位机验收、12 条静态断言），**不把"团队规划"说成"我实现"**，也不把仿真说成实测。

## 9. 使用建议（给候选人的 8 条实操建议）

1. **按岗位挑版本，不要一次投全文。** 嵌入式软件岗投 §4，FAE 投 §5，机器人控制岗投 §6，硬件/联调岗投 §7；§1–§3 放在项目列表或自我评价里。**§7 只能用于明确写着"设计经验可"的岗位**——它整节都是设计计算，投给需要"做过实物"的岗位会被一眼看穿。

2. **先复算，再写。** 写进简历前，请亲手算一遍并留下算式：`0.5 mV/N × 201 = 100.5 mV/N`、`3.3 V/4096 = 0.806 mV`、`0.806/100.5 ≈ 8.0 mN`、`24 V/2 Ω ≈ 12 A`、`2.2 N ÷ 0.008 N/count ≈ 274 counts`。**只要有一个算不出来，就把它从简历上删掉。** 仓库里现有的四处不一致（50 N vs 10 N 前端、8.0 mN vs 12 mN、自适应默认开关、DMA 缓冲 16 vs 32）必须在报出去之前内部统一。

3. **准备好"证据文件包"，但不要伪造。** 最强的一件是 **host 仿真真跑过的证据**：`build/host/tea_picking_robot_host.exe` 与它写出的 `data/logs/host_scenario_A.csv`（约 5021 行、1 kHz 逐周期、十一列）——**并在出示时主动说明它是 host 仿真二进制、不是真机**（行数会随重新生成变化，当场核实）。其次是 `host/selftest.py` 的运行输出、`config.h` 的 12 条静态断言、状态机转移表、7 个场景的定义。**出示 `data/logs/monitor_selftest.csv` 时一定要主动说明：它只是 3 秒无头演示，`state` 只到 IDLE、位置与力全为 0**——不说明就等着被追问。**永远不要把"设计目标"包装成"测试报告"**：面试官打开 CSV 发现全零，证据就变成了反证。
   另外：这个仓库**仍在被并行补齐**（撰写本文件期间就新增了 `main_host.c`、`platform_stm32f407.c`、host 可执行文件与轨迹 CSV）。**投递前请把 §声明5 的"缺失清单"重新核对一遍**——不要把已经补上的文件说成"没有"，那和编造数据一样致命，而且更尴尬。

4. **主动使用三类标注这个词。** 面试时自己先说："这个数字是设计目标，这个是代码里的阈值，这个是仿真结果，实测都还没有。" 主动划线的人，可信度远高于被追问才承认的人；而且这一步会把面试节奏带到你的强项（架构、推理、方法）上。

5. **把"没有"也说成信息。** 没有板、没有 ISR 实测周期、没有覆盖率、没有 CI、没有单元测试——直接说，并紧跟一句"所以我把可测性做进了架构：单一硬件接缝、host 物理模型后端、可注入日志与时钟"。**缺口 + 应对，是资深工程师的表达方式；缺口 + 沉默，是危险信号。**

6. **别把团队的活说成自己的。** 视觉系统、机械结构、PLC 集成很可能是别人做的——写成"与视觉系统对接 `SET_TARGET`（10 字节、置信度 0–100、`target_id` 可关联日志）"和"为 PLC 提供 Modbus RTU 从站"，比写成"我做了视觉系统"安全得多，也专业得多。

7. **对"1 Hz 节拍 / 2.2 N / 提升 40% / 破损率 1%"这类数字，统一口吻。** 一律写成"**设计目标**"，并补一句它的含义（节拍 = 单芽全流程时间预算的上限；2.2 N = 软限 3.5 N 与硬限 5.0 N 之下的工作点）。**简历上永远不要出现没有来源的"实测"**——尤其是这两个具体数字（破损率 ≤ 1%、效率提升 40%）在仓库里根本不存在。

8. **面试前 30 分钟只做一件事：过一遍第 8 节。** 十五条硬问题里，凡是答不上"证据在哪个文件"的，就把简历上对应的那一条删掉或降级为设计目标。**一份删掉了三个数字但每个数字都站得住的简历，比一份数字漂亮但经不起三问的简历，通过率高得多。**
