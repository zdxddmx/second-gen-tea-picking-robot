# `data/` — generated output

Nothing in this directory is source. Everything here is produced by running the
project, and everything here can be regenerated from scratch.

```
data/
├── logs/       CSV traces, text logs and JSON metric dumps
└── results/    figures (PNG)
```

## Why the contents are not committed

Two reasons, and the second is the important one.

1. **Size.** One eight-second run at 1 kHz is about 8,000 rows, and the full
   seven-scenario sweep writes roughly 4 MB of CSV and 1.5 MB of figures. A
   repository that carries that much generated output becomes slow to clone and
   impossible to review.

2. **Honesty.** A checked-in trace is a claim about a run that a reader cannot
   verify, and it can silently go stale the moment a constant changes. A trace
   that is regenerated by a documented command is evidence; a trace that sits in
   a directory is decoration. Every result quoted in the README and in
   `docs/12_results_analysis.md` can be reproduced with the commands below, and
   the repository deliberately stores the *method* rather than a snapshot of its
   output.

## How to regenerate

```bash
# Complete demonstration: build, run the C firmware, run the Python model,
# cross-check them, and draw the curves.
python scripts/run_demo.py

# Firmware traces for all seven scenarios, with the criteria table.
./scripts/run_scenarios.ps1 -Csv

# Python simulator: five time-series figures plus a scenario comparison.
python simulator/main.py --scenario all

# A single firmware run with a trace.
./build/host/tea_picking_robot_host.exe --scenario A --duration 8 \
    --csv data/logs/trace_A.csv
```

## What each file is

| Pattern | Produced by | Contents |
|---|---|---|
| `logs/demo_firmware_*.csv` | `scripts/run_demo.py` | Per-control-period trace: `t_ms, ref_mrad, pos_mrad, vel_mrad_s, force_n, gap_mm, duty_permille, current_ma, state, grip_state, fault, cycle` |
| `logs/demo_firmware_*.log` | `scripts/run_demo.py` | The firmware's complete log stream, in the same format the target's debug UART emits |
| `logs/host_scenario_*.csv` | `scripts/run_scenarios.ps1 -Csv` | One trace per scenario, same column layout |
| `logs/scenario_*_log.csv` | `python simulator/main.py` | The Python model's per-tick recording |
| `logs/scenario_*_metrics.json` | `python simulator/main.py` | Computed metrics: rise time, overshoot, settling time, steady-state error, peak force, force RMSE, damage index |
| `results/*.png` | both simulators | Time-series curves and scenario summaries |

## A note on comparing the two traces

The firmware CSV and the simulator CSV have the same column names **on purpose**,
so they can be plotted against each other or differenced without a conversion
step. They will not be numerically identical, and they are not supposed to be:

* the two plant models use different integration schemes for the current,
* the firmware's trace is sampled at 1 kHz and the simulator's at its own rate,
* the simulator adds optional sensor noise.

What *must* agree is what the controllers regulate to — the grip force setpoint,
the absence of over-limit excursions, and the stability of the final state. That
comparison is what `scripts/run_demo.py` performs and prints.
